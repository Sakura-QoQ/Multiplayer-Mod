# API 与错误码规范

项目没有 HTTP 监听端口；房间服务继续使用“4 字节大端长度 + UTF-8 JSON”的 TCP 帧。`status` 使用标准 HTTP 状态码语义，使 TCP 服务、本地桥和 Mod 使用同一套成功与失败结构。

## 通用响应

```json
{
  "success": true,
  "status": 200,
  "code": 0,
  "message": "OK",
  "data": {},
  "requestId": "1"
}
```

- `success`：操作是否成功。
- `status`：HTTP 语义状态码，例如 `200`、`400`、`403`、`404`、`409`、`413`、`422`、`429`、`500`、`503`。
- `code`：业务错误码；成功固定为 `0`。
- `message`：适合日志记录的简短说明，业务逻辑不得依赖该文本。
- `data`：成功数据；失败时为 `null`。
- `requestId`：房间服务器请求标识；广播事件允许为 `null`。

房间服务器的新请求使用下列信封。服务器仍接受旧版裸请求，并对该连接返回旧版裸响应和广播；只有发送过 `api.request` 的连接才会收到标准信封，便于服务端与玩家 Mod 独立滚动升级：

```json
{
  "type": "api.request",
  "requestId": "1",
  "data": { "type": "room.list", "modVersion": "v1.1.11" }
}
```

`room.list` 的成功数据带独立服务器配置中的 `serverVersion` 和 `requiredModVersion`；新版客户端在 `room.enter` 中提交自己的 `modVersion`。服务器构建时嵌入 `server/version.json`，不读取 `mod/info.json`；版本不一致时仅在客户端弹出建议更新提示，仍可列出房间和进入。为第一次上线握手保留滚动升级窗口：没有版本字段的 1.0.1 及更早客户端暂时允许进入；支持握手的版本也允许不匹配连接。

## 服务端错误码

| 分段        | 领域       | 已定义错误码                                                                                                                                                                                                                                                   |
| ----------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `1001-1999` | 协议与输入 | `1001` JSON 无效，`1002` 请求无效，`1003` 未知命令，`1004` 帧过大，`1005` 请求速率超限                                                                                                                                                                         |
| `2001-2999` | 房间与成员 | `2001` 房间数上限，`2002` 房间 ID 无效，`2003` 已存在，`2004` 不存在，`2005` 密钥错误，`2006` 已满，`2007` 已在房间，`2008` 未入房，`2009` 公共房不可用，`2010` 私有房，`2011` 添加成员失败，`2012` 旧服务端版本不兼容错误（仅保留解码兼容，新服务端不再发送） |
| `3001-3999` | 转发与玩家 | `3001` 负载无效，`3002` 玩家不存在                                                                                                                                                                                                                             |
| `4001-4999` | 世界同步   | `4001` 场景无效，`4002` 睡眠模式无效                                                                                                                                                                                                                           |
| `5001-5999` | 管理接口   | `5001` 无权限                                                                                                                                                                                                                                                  |
| `6001-6999` | 服务端系统 | `6001` 内部错误                                                                                                                                                                                                                                                |

## Mod/本地桥错误码

| 分段        | 领域         | 已定义错误码                                                                      |
| ----------- | ------------ | --------------------------------------------------------------------------------- |
| `1001-1999` | IPC 与运行时 | `1001` 未知命令，`1002` 请求无效，`1003` 超时，`1004` 桥不可用，`1005` 未预期错误 |
| `2001-2999` | 联机会话     | `2001` 连接失败，`2002` 已运行，`2003` 未连接                                     |
| `4001-4999` | 数据发送     | `4001` 发送失败                                                                   |

业务代码只能判断 `success` 或数值 `code`，不得判断 `message`。新增业务应申请新的千位分段；同一领域内不得复用已经发布的错误码。

## 存档边界

当前桥接 API 只处理网络会话，不提供创建、准备、提交、重命名或恢复线上存档的命令。Mod 通过原版 `LoadSaveWindow` 自动读取默认 `AutoSave`；旧 `MPOnline`/`MPActive` 只保留在磁盘供人工恢复，桥接启动和退出时都不会访问。

## 1.1.13 共享日期/时段

公开房间先通过现有 `serverSceneRequest` 的可选 `calendarQuery: true` 探测能力。新服务器返回 Peer 0 的 `calendarReady`（尚未初始化）或当前 `roomCalendar`；旧服务器忽略可选字段，客户端保留旧时间行为，不发送旧服务器不认识的新类型。脚本重载后重新探测，不要求更新网络桥。

| 消息            | 来源            | 字段与语义                                                        |
| --------------- | --------------- | ----------------------------------------------------------------- |
| calendarPropose | 客户端 → Peer 0 | day 整数 0–1000000；timeOfDay 整数 0–3；expectedRevision 非负整数 |
| calendarReady   | Peer 0 → 客户端 | 确认支持共享日历，但房间还没有种子                                |
| roomCalendar    | Peer 0 → 客户端 | day、timeOfDay、revision；revision 为递增正整数                   |

首份已完成原版读档的数据以 expectedRevision=0 初始化日历。之后比较交换版本：版本匹配、日期更晚或同一天时段发生改变才提交；过期或回退日期的提案只返回当前状态。后来加入者日期较晚时推动房间，较早者通过 AddDay 逐日追赶。客户端先对齐一次，再观察原版剧情已经完成的同一天时段变化，因此不会用旧房间值撤销原版 SetTime。个人任务、联系人、背包不属于协议；逐日追赶会执行原版回调，可能推进或使个人限时剧情过期。

普通公开成员不能发送 roomCalendar/calendarReady 冒充权威。旧 worldTime/serverTimeSeed/serverTimeCommit 仍忽略；新方案不运行独立的秒级房间时钟。本地直连沿用同样的数据结构，Peer 0 玩家房主初始化并裁决版本。
